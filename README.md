# SOULHEALTH AI 健康科研平台 Demo

覆盖需求闭环：**上传检查报告 → 结构化健康档案 → AI 健康 Agent 分析（风险识别 / 知识匹配 / 机制解释 / 生物计算计划）→ 《个性化健康分析报告》+《药食同源代茶饮建议》（docx + md）**。
五个阶段已全部交付：方案与选型｜摄取层+档案库｜知识库+Agent+报告生成｜生物计算+定制前端｜**产品化（身份找回·持久档案·真实优先·多病种泛化·健康问答）**。

## 快速开始

```bash
cd soulhealth-demo
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env                                    # 可整体留空

python tests/test_offline.py     # 摄取/档案冒烟：12 项（零依赖零网络即可跑）
python tests/test_stage3.py      # Agent 全链路：32 项
python tests/test_stage4.py      # 生物计算与前端资源：10 项
python tests/test_stage5.py      # 身份证匹配 + 手动录入 + 目录全量与门禁 + 辨证组方引擎 + 安全联动 + 问答历史：90 项
python tests/test_auth.py        # 登录鉴权：密码哈希/令牌/管理员播种/多用户档案隔离：23 项
python run_demo.py --fresh       # 命令行一键端到端演示（无 key 时自动显式 MOCK 并提示）
python run_api.py                # 图形界面 → http://127.0.0.1:8000/（API 文档 /docs）
```

**运行模式（阶段五起真实优先）**：配置 `ANTHROPIC_API_KEY` → real（健康问答走真实模型）；显式 `SOULHEALTH_MOCK=1` → 演示样例（问答如实拒答不给假回答）；两者皆无 → 问答接口返回明确配置指引，**绝不悄悄返回假答案**。生物计算默认 real（AlphaFold DB / UniProt / Ensembl 免密钥公开 API）；EVO2 打分需 `NVIDIA_API_KEY`，未配置时该项如实标记 skipped，但变异位点/等位基因仍为 Ensembl 实时数据。

**身份匹配改为纯身份证后四位（本轮澄清修正）。** 上一版把"图片抽取"和"姓名+性别+年龄±2岁模糊匹配"两件事混在一起处理错了：图片上传/视觉抽取功能予以保留，改动的只是身份匹配规则。`find_or_create_patient()` 现在**唯一**依据"姓名 + 身份证后四位"精确匹配（同姓名+同后四位=同一人，年龄怎么变都认得出）；**不再有任何模糊匹配**——未提供身份证后四位时，系统不做猜测，每次都新建一条档案，前端会明确提示"未填后四位，下次同名会新建一个档案"，引导用户尽量填写。这样彻底避免了"同名同性别年龄相近"场景下把两个不同人错误合并为一档的风险。

**数据入口：图片上传 + 手动录入两种方式并存。** 图片上传走视觉模型抽取（`POST /api/documents/upload`），未配置密钥或模型不支持读图时会给出明确诊断（含 `/api/selftest/vision` 自检入口），不会悄悄编造抽取结果。手动录入作为补充/替代（无密钥或不想依赖模型时可用）：
- 化验指标（`.../observations`）：code/数值/单位/参考范围，异常标记按参考范围自动判定；
- 影像/查体所见（`.../findings`）：脏器、所见描述、异常关键词——对应报告单"检查所见"逐脏器段落；
- 诊断提示（`.../impressions`）：照抄报告单底部"超声提示/诊断意见"原话（如"脂肪肝"）——与"所见"是不同字段，风险规则里"超声提示脂肪肝"专门依赖这个字段。

**登录鉴权：管理员 / 普通用户两种角色（本轮新增）。** 新增 `app/auth.py`（纯标准库 PBKDF2 密码哈希 + HMAC 自签令牌，零第三方依赖）与 `users` 表：
- 首次启动自动创建一个管理员账号，密码随机生成并打印在服务端控制台（仅显示一次，`SOULHEALTH_ADMIN_PASSWORD` 可固定密码用于自动化部署）；
- 普通用户可自助注册（`POST /api/auth/register`，固定角色为 user，防止任何人给自己开管理员权限）；
- **档案按用户隔离**：`patients` 表新增 `owner_id`，普通用户只能看到/操作自己名下的档案，管理员可查看全部；同姓名+同身份证后四位在不同用户名下不会互相"找回"到对方的档案；
- 管理员面板（前端右上角"管理员面板"按钮）：查看全部用户、创建用户（可指定角色）、停用/启用、删除（删除用户不删档案，档案 `owner_id` 置空由管理员承接可见性）；
- 令牌为自制的"载荷+HMAC签名"结构（非标准 JWT 但同思路），12 小时过期（`SOULHEALTH_TOKEN_TTL_HOURS` 可调），**`SOULHEALTH_SECRET_KEY` 使用默认开发密钥时前端会有明显提示**，生产部署必须设置为随机长字符串，否则任何人可伪造登录令牌。这是教学/演示级实现，没有令牌吊销列表、刷新令牌轮换等能力，如实说明。

## 阶段三设计要点

**组方可解释可审计。** 槽位式组方（君2·臣3·佐2·使1），每味带用途/性味/命中标签/禁忌；《药食同源目录》作硬门禁——参考方中的玉米须（属保健食品原料名单）被自动跳过、由赤小豆承接利水之用，替换全程留痕并写入报告附表。这既是合规能力，也是演示亮点。

**合规闸不可绕过。** `compliance.py` 维护违禁话术清单（速效/治愈/无任何副作用/数字时间承诺等），报告落盘前 `assert_clean`，违规直接抛错阻断；同一清单被 32 项测试引用做红线回归。就医提示与"不替代诊断"为必备要素，缺失同样阻断。

**docx 零依赖。** `docx_writer.py` 纯标准库直写 OOXML（标题/多级导航标题/富文本段/要点/表格/提示框），已通过 OOXML XSD 校验与 LibreOffice 渲染验证；同一块模型同时渲染 markdown，方便前端预览与 diff。

**机制层诚实标注。** 机制链为人群水平机制学解释，报告明示"未使用任何个人基因数据"；TM6SF2 的 UniProt 号留待阶段四客户端在线解析而非硬编码。生物计算调用以 planned 状态入库，阶段四执行后回填。

## 阶段四设计要点

**前端。** 原生 HTML/CSS/JS 三件套（零构建、离线可跑），由 FastAPI 直接托管。设计取"食养 × 计算生物学"双世界语言：宣纸青白底、青瓷主色、黛蓝承载生物计算、朱砂仅用于合规批注（目录替换戳记、异常指标）；标题用衬线呼应纸质报告单。签名元素是左侧**经络式流程轴**：点击"开始智能分析"后，Agent 六节点随真实 trace 逐一点亮并标注毫秒耗时——把"AI 在做什么"变成可讲解的画面。移动端自适应、respects prefers-reduced-motion。演示动线：载入演示患者（一键建档+注入两份单据）→ 开始智能分析 → 下载报告。

**生物计算。** `SOULHEALTH_BIOCOMPUTE=mock|real` 切换。mock（默认）读演示缓存，字段结构与真实返回对齐，前端与报告全部打「演示缓存」标签，绝不冒充真实数据；real 下 AlphaFold DB 走 EMBL-EBI 公开 API（免密钥），TM6SF2 这类未硬编码 UniProt 的基因先经 UniProt REST 在线解析——MOCK 模式该项诚实展示为"待在线解析"。单项失败不阻断整体分析。

**EVO2 真实接入说明。** 默认端点为 NVIDIA NIM 托管 EVO2（需 `NVIDIA_API_KEY`）；不同 NIM 版本的请求/响应字段可能有差异，客户端做防御式解析，结构不符时以 status=error 返回明确修正位置（`app/biocompute/evo2_client.py` 的 `_real_call` / `_ll`）。私有化部署时用 `SOULHEALTH_EVO2_URL` 覆盖端点即可。演示打分使用合成参考序列，不涉及任何用户个人基因数据。

## 阶段五设计要点（产品化）

**患者身份：按人找回，不再裂档。** `find_or_create_patient(name, sex, age)`：姓名归一化（去空格、大小写不敏感）+ 性别精确 + 年龄 ±2 岁容差匹配既有档案，命中即复用并更新（年龄随访更新、身高体重回填）；找不到才新建。同名同性别年龄相近的两个真实的不同人需人工区分（可在姓名后加标注），这是姓名匹配方案的固有边界，已如实说明。**真实姓名只落本地 SQLite，绝不发往任何外部服务**；对外分析与报告默认使用化名（`SOULHEALTH_REPORT_REAL_NAME=1` 可开启报告打印真名）。

**长期记忆有了入口。** 前端"00 我的健康档案"：姓名搜索 + 最近使用列表（资料/分析计数），点击即载入全部历史；`localStorage` 记住当前档案，刷新/重开浏览器自动恢复会话。历次分析入库时补存 `formula_json` 与 `trace_json`，前端点击任意历史分析即可完整回放（流程轴 + 四区结果 + 报告下载）。备注（症状描述）作为需求文档的输入类型之一入档。

**真实优先，诚实降级。** MOCK 从"默认兜底"降级为"显式开关"：只有 `SOULHEALTH_MOCK=1` 才用演示样例；无 key 且非 MOCK 时，抽取与问答返回带配置指引的明确错误，**不会悄悄给假答案**。生物计算默认真调：AlphaFold DB / UniProt / Ensembl 均为免密钥公开接口；EVO2 真实路径为 **Ensembl 实时解析 rsID → 真实基因组 121bp 序列窗口（ref/alt）→ NVIDIA NIM 打分**，无 NVIDIA key 时打分项 status=skipped 并如实说明，但位点/等位基因仍是真数据。真实模式下任何外呼失败均 status=error 附原因，不回落演示数据冒充结果。

**前端样式与结构对齐。** 早期迭代留下过 CSS 选择器与 HTML/JS 实际类名不一致的问题（如 `.masthead` vs `.hero`、未定义的 `--indigo` 变量），导致头部、表单、问答气泡等大量样式失效。已按 index.html/app.js 的真实类名全量重写 app.css 并做过交叉核对（零漏配），同时收紧了间距节奏、统一了圆角/阴影/字号比例，长表格加了横向滚动容器，toast 提示条改为可滚动、可手动关闭。

**机制文案精确性。** 修正过一处误导性表述：单纯「肝酶升高」（无脂肪肝影像证据）曾被归入脂肪肝特异性机制通路，报告里会出现「PNPLA3」「脂肪从头合成」等其实并未被选中的机制实体描述。现拆分为独立的通用肝损伤机制组：单纯肝酶升高给出「病因多样、需医生鉴别」的中性表述；只有真正存在脂肪肝影像/肥胖等信号时才关联脂肪堆积特异性机制。`tests/test_stage5.py` 用同一患者的两种数据组合做了正反对照回归。

**弱数据与安全兜底。** BMI 低于 18.5 会识别为「体重偏低」并给出营养/就医方向建议（而非沉默地报「无显著风险标签」）；自述症状（备注）进入风险区作 info 级提示并写入报告原文，但明确不作病因推断。组方设了安全门禁：只有当**针对性槽位**被风险标签命中时才组方——体重偏低者、仅有主诉症状者一律不出代茶饮，避免把减脂方向的配伍推给不该用的人。档案中没有客观检查资料时，报告首段即标注「数据充分性提示」。

**药食同源目录全量化（本轮做实）。** 目录从 35 味扩充至 **116 种**，覆盖国家卫健委 2002 年《既是食品又是药品的物品名单》87 种（含动物类）、2014 年试点品种、2019 年试点转正 9 种（党参/黄芪/西洋参/灵芝/肉苁蓉/铁皮石斛/山茱萸/天麻/杜仲叶）、2023 年增补 4 种（地黄/麦冬/天冬/化橘红），每种均含性味归经、功效、安全剂量区间与禁忌，status 按批次标注。**目录完整性与组方安全性分层保证**：香料类（丁香/花椒/肉桂等，`seasoning`）、动物类（乌梢蛇/牡蛎/阿胶等，`animal`）、毒性明确类（白果/桃仁，`toxic_caution`）如实收录进目录但永远不进入组方候选；苦杏仁按目录名「杏仁（甜、苦）」收录说明，代茶饮一律只用甜杏仁；茯神因官方目录文字仅载「茯苓」，如实标注口径存疑并按目录外处理。门禁判定改为「药食同源目录」前缀匹配以兼容批次后缀（`in_catalog` 与 `catalog_check` 已统一，曾有一处不一致会导致全量品种被误判目录外，已修复并有回归测试锁定）。目录数据按《中国药典》与公开文献整理，**投产前仍须由执业中医师/药师逐条复核**，README 与 JSON 内均如实标注。

**组方引擎重构为「辨证 → 立法 → 底方 → 加减」（本轮核心）。** 对齐真实中医开方流程，废弃"标签→散装药材拼装"的旧槽位模式，新架构（`app/knowledge/classic_formulas.py` + 重写的 `formula.py`）四步：① **主证决策**——多证共存时按治则优先级取主证（外感先解表、急则治标、慢性调理靠后），无自述证型但有代谢风险则启用兜底底方；② **匹配经典底方**——桑菊饮（《温病条辨》，去连翘）、参苓白术散（《局方》，去白术砂仁）、酸枣仁汤合百合地黄汤意（《金匮要略》，去知母川芎）、生脉饮合玉屏风意（去五味子白术防风）、杏苏散（去半夏前胡枳壳）、藿香正气散（去半夏厚朴）、桔梗汤加味（《伤寒论》）、益胃汤（去沙参）、润肠饮（自拟，取五仁丸意，桃仁禁）、清利饮（自拟，取四妙散意——苍术黄柏牛膝均不在目录，如实标注无法化裁复现）、保和丸（《丹溪心法》，去神曲半夏连翘）——**每个底方逐味核对在药食同源目录内，因目录限制去掉的原方药味全部留痕，不假装开出了原方**；③ **兼证兼风险加减**——每条加减附依据（兼血糖加桑叶葛根、兼尿酸加利湿泄浊之品等），最多 4 条防药味堆叠，主证为外感时按「外感忌补」治则自动跳过黄芪党参等补益之品并留痕；④ **安全层**——目录门禁替换、AVOID_IF 禁忌规避（底方内的桂圆肉/蜂蜜/甘草遇对应风险同样规避并留痕）、总量封顶 10 味。返回结构新增 formula_name / source / treatment_principle / primary_syndrome / modification_log，报告新增「加减与化裁依据（逐条留痕）」章节，前端组方块显示方名、治则与可展开的化裁明细——**从主证决策、底方选择、每一条加减到每一次规避，全程有据可查**。

**证型扩至 10 组、配伍遵循治则。** 在失眠/咽喉/气虚之外新增 7 组：湿热内蕴（蒲公英/栀子为君，薏苡仁淡渗制衡苦寒）、阴虚津亏（麦冬/玉竹/铁皮石斛甘寒养阴）、肠燥便秘（火麻仁/郁李仁润下不峻下）、风热外感初起（金银花/薄荷辛凉解表，芳香品后下）、脾虚湿盛（炒白扁豆/芡实健脾固涩）、咳嗽有痰（甜杏仁/桔梗/化橘红宣肺化痰）、暑湿困表（藿香/香薷芳香化浊）。安全机制：**便秘与便溏证型互斥**（药性相反同现时按安全优先保留便溏方向、不予润肠品，取舍留痕）；蜂蜜/大枣/桂圆肉/桑椹与血糖异常标签联动自动规避；煎服法按方内成分动态提示（芳香品后下、蜂蜜温调不同煮、苦寒品中病即止）。

**中医证型也纳入组方。** 新增 `app/knowledge/tcm_syndrome.py`：从患者自述文本中用关键词匹配识别失眠/咽喉不适/气虚三类证型（`insomnia_pattern` / `throat_pattern` / `qi_deficiency_pattern`），与化验/影像驱动的生物医学风险标签严格分离——证型不写入"健康风险识别"章节、不构成诊断，只用于丰富组方引擎的可覆盖场景。组方引擎（`formula.py`）新增 8 个证型槽位（酸枣仁/茯神/百合/桂圆肉/桔梗/金银花/黄芪/党参/山药/西洋参/灵芝/佛手等 19 味新增原料），并支持 per-candidate 剂量覆盖（同一槽位不同候选原料可以有不同安全剂量，而不是被迫共用一个数字）。药食同源目录从 16 味扩充到 35 味，标注了"试点/增补目录"品种（黄芪、党参）需核对属地最新公告；**尚未覆盖官方全量约 106 味清单，这是已知的覆盖缺口，非虚假宣称完整**。

**问答系统引用历次分析趋势（本轮新增）。** 此前健康问答只取"最近一次"分析的风险标签作为上下文，回答不了"和上次比是不是好转了"这类纵向问题。现在 `qa.py` 的上下文构造会带上最近 5 次分析记录的时间序列，以及同一指标跨多次记录的数值变化，模型能引用具体日期和数值作答；历史记录不足时会如实说明数据不足，不臆测趋势。

**换一个病种照样工作。** 规则引擎扩至 15 组（血糖/HbA1c、血脂四项、尿酸分性别、血压、血肌酐、血红蛋白、通用影像所见结节/结石/囊肿/息肉/占位…）；机制实体与通路组均带 `triggers`，随风险标签自动切换（糖脂患者 → TCF7L2/LPL/APOE/ABCG2/SLC2A9，而非固定 NAFLD 四件套）；组方槽位带 `indications` 条件与 `avoid_if` 冲突规避（高血压者不用甘草），肝脂患者与糖脂/尿酸患者得到不同配方，报告的辨证/靶点/复查/饮食章节同步条件生成；无风险标签时不硬凑配方、只出健康报告并明确说明。`tests/test_stage5.py` 用"46 岁男性糖脂尿酸异常"第二病种全链路回归。

**健康问答（真实回答问题）。** `POST /api/patients/{pid}/ask`：以脱敏档案（化名+结构化指标/影像/备注/上次风险标签）为上下文真实调用 Claude；系统提示词约束"不诊断、不开处方、引用档案数据、无绝对化疗效"；回答落地前过 `compliance.lint`，命中违禁表述带反馈重试一次，仍不合规则拦截报错。

## 故障排查：上传图片报「模型没收到图像」

先跑自检（一键判定所配模型是否真的能读图）：

```bash
curl http://127.0.0.1:8000/api/selftest/vision     # 或点前端「02 数据输入」里的「视觉链路自检」
```

系统会发一张**已知颜色的探测图**问模型看到什么颜色：

- `ok: true` → 视觉链路正常，问题在具体那张图（看报错里的诊断字段：字节数、media_type、模型名）。
- `ok: false` 且模型回「无图」→ **所配模型收不到图像**。三种常见成因：① `SOULHEALTH_LLM_MODEL` 指向了不支持视觉输入的模型，改用 `claude-sonnet-4-6` 等视觉模型；② 中间网关 / 反代 / 兼容层把非文本内容块剥离了；③ 密钥指向纯文本端点。
- `ok: false` 且调用报错 → 密钥、模型名或出网连通性问题，报错原文即为线索。

抽取侧的设计原则是**宁可失败也不编造**：模型一旦表示没收到图像，立即中止并抛出带诊断信息的错误（不会浪费第二次重试，更不会落一份全 null 的假单据入档）。发请求前还会做前置校验：空文件、体积超限（图片 3.6MB / PDF 30MB）、格式无法识别（如 HEIC）都会在本地就被拦下并给出转存指引；media_type 由**文件魔数**嗅探而非扩展名决定，改过名的截图也能正确识别。
